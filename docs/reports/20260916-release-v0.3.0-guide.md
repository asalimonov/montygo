# Releasing montygo v0.3.0

Date: 2026-09-16. Audience: the maintainer running the release. Every command is run by you.

This release publishes three things:

1. the Go module `github.com/asalimonov/montygo` at `v0.3.0`;
2. the image `ghcr.io/asalimonov/monty-server:0.3.0`, attached to this repository;
3. `montygo.NewDocker`, which runs that image at the version of the package.

They are one release on purpose: `NewDocker` derives its image tag from the package version, so the module and the image MUST carry the same number.

## 0. State before you start

| Fact | Value |
|---|---|
| work branch | `fix/refactoring-v0.3.0-pre` |
| default branch | `main` |
| tags on the remote | none |
| local tag `v0.2.0` | points at `8b86307`, which is not an ancestor of `main` |
| published Go versions | none |
| GHCR packages | none |

`v0.2.0` was tagged on the pre-squash branch, so it is not in `main`'s history. `v0.3.0` is the first tag `main` can reach. Nothing depends on the old tag; `scripts/version.sh` only considers tags reachable from `HEAD`.

Decide what to do with it:

- **Recommended:** do not push it. Delete it locally and point the changelog's comparison link at the first commit.

  ```bash
  git tag -d v0.2.0
  ```

  Then edit the last line of `changelogs/v0.3.0.md`:

  ```
  Full changelog: [890f0f9…v0.3.0](https://github.com/asalimonov/montygo/compare/890f0f9...v0.3.0).
  ```

- Alternative: `git push origin v0.2.0`. The commit exists on the remote branch `feat/dockerized-runtime`, so the link resolves, but `go get …@v0.2.0` would then serve code that is not an ancestor of `main`.

## 1. Verify the working tree

Run the full gate on `fix/refactoring-v0.3.0-pre`. Each command must pass.

```bash
export GOTOOLCHAIN=local
make check-pins
make test-scripts
go vet ./...
golangci-lint run ./...
go test -count=1 ./...                      # native and wasm
go test -race -count=1 ./...
go mod tidy -diff
(cd examples && go vet ./... && go mod tidy -diff)
(cd tests/network && go vet ./... && go mod tidy -diff)
MONTY_EXAMPLES_BACKEND=native make examples
MONTY_EXAMPLES_BACKEND=wasm make examples
make server-check                            # set MONTY_BIN to the native worker
make docker-build                            # also tags ghcr.io/asalimonov/monty-server:<version>
make docker-build-pyclient
make test-docker                             # root suite on the docker backend
make test-network
```

`make docker-build` needs Docker's containerd image store for two platforms. Without it, use `PLATFORMS=linux/arm64`.

## 2. Merge to `main`

```bash
git push -u origin fix/refactoring-v0.3.0-pre
gh pr create --base main --title "Docker-managed monty-server, supervisors and session rotation" --body-file changelogs/v0.3.0.md
gh pr checks --watch
```

CI runs `test` on Linux and macOS, `docker`, and `docker-arm64`. All must be green. Merge when they are:

```bash
gh pr merge --squash --delete-branch
```

## 3. Tag the release

```bash
git switch main
git pull --ff-only
git status --porcelain     # MUST be empty
make version               # prints 0.0.0-<hash> until the tag exists
```

Tag the merge commit and push the tag:

```bash
git tag -a v0.3.0 -m "montygo v0.3.0"
git push origin v0.3.0
make version               # now prints exactly 0.3.0
```

`make version` MUST print `0.3.0` with no `-<hash>` and no `-dirty`. If it does not, the tag is not on `HEAD` or the tree is dirty; fix that before continuing, because the version is stamped into the image and the server.

## 4. Watch the release job

The tag triggers CI again, including the `release` job. It runs only after `test`, `docker` and `docker-arm64` pass, and it:

1. requires a clean tree;
2. requires `scripts/version.sh` to equal the tag without `v`, and `changelogs/v0.3.0.md` to exist;
3. pushes `ghcr.io/asalimonov/monty-server:0.3.0` for `linux/amd64` and `linux/arm64`, with an SBOM and a provenance attestation.

```bash
gh run list --limit 3
gh run watch "$(gh run list --event push --limit 1 --json databaseId --jq '.[0].databaseId')"
```

The whole tag run takes roughly 60–90 minutes.

## 5. Make the image usable

A first push creates a **private** GHCR package, even from a public repository. `NewDocker` pulls anonymously, so the package MUST be public.

1. Open `https://github.com/users/asalimonov/packages/container/monty-server/settings`.
2. Under "Danger Zone", choose **Change visibility → Public**.
3. Under "Manage Actions access", confirm the repository `asalimonov/montygo` has access. The image already carries `org.opencontainers.image.source`, so the package shows on the repository page once it is public.

Verify anonymously, ideally on another machine or after `docker logout ghcr.io`:

```bash
docker pull ghcr.io/asalimonov/monty-server:0.3.0
docker run --rm ghcr.io/asalimonov/monty-server:0.3.0 --version    # prints 0.3.0
```

## 6. Publish the Go module

The proxy serves the tag on first request. Warm it and confirm:

```bash
cd "$(mktemp -d)"
go mod init release-check
GOPROXY=https://proxy.golang.org GOTOOLCHAIN=local go get github.com/asalimonov/montygo@v0.3.0
GOPROXY=https://proxy.golang.org go list -m -versions github.com/asalimonov/montygo   # lists v0.3.0
```

Then open `https://pkg.go.dev/github.com/asalimonov/montygo@v0.3.0` once, which queues the documentation build.

## 8. Prove the whole thing works

From a clean directory, with no montygo checkout and no local image:

```bash
docker image rm ghcr.io/asalimonov/monty-server:0.3.0 2>/dev/null
cd "$(mktemp -d)"
go mod init smoke
go get github.com/asalimonov/montygo@v0.3.0
cat > main.go <<'EOF'
package main

import (
	"context"
	"fmt"

	"github.com/asalimonov/montygo"
)

func main() {
	ctx := context.Background()
	pool, err := montygo.NewDocker(ctx, montygo.DockerOptions{MaxProcesses: 2})
	if err != nil {
		panic(err)
	}
	defer func() { _ = pool.Shutdown(ctx) }()
	value, err := pool.Run(ctx, "sum(range(10))", nil)
	fmt.Println(value, err)
}
EOF
go run .
```

It MUST print `45 <nil>`. The pull happens on the first run, because `BindingVersion()` is `0.3.0` and no local image matches. Check that nothing is left behind:

```bash
docker ps -a --filter label=io.montygo.supervisor
```

## 9. After the release

- Announce or link the release notes as you see fit.
- The next development build reports `0.3.0-<hash>`; `NewDocker` then tries that exact tag, finds nothing, and falls back to `0.3.0`. That is intended.
- `make docker-build` tags `ghcr.io/asalimonov/monty-server:<version>` locally, so a development build of the server is picked up before the published release.

## Failure modes seen while preparing this release

| Symptom | Cause | Fix |
|---|---|---|
| `test (ubuntu-latest)` fails at "Vulnerability check" with `golang.org/x/vuln@v1.8.0 requires go >= 1.26.0` | `golang/govulncheck-action` installs `govulncheck@latest`, and `x/vuln` v1.8.0 needs Go 1.26 while CI pins Go 1.25 with `GOTOOLCHAIN=local` | fixed in this branch: the step installs `govulncheck@v1.7.0` directly |
| The `release` job fails at "Require a clean tree" | the job checked out `pydantic/monty` into `monty-src/`, which `git status` reports as untracked | fixed in this branch: the release job builds the image from the pinned `MONTY_REV` fetch and does not check upstream out; `/monty-src/` is also git-ignored |
| The image version carries `-dirty` | the build ran on a tree with untracked or modified files | build from a clean checkout of the tag |
| `NewDocker` fails with "cannot derive a monty-server image tag" | the binary was built with a directory `replace` and no stamp, so `BindingVersion()` is `(devel)` | set `MONTYGO_DOCKER_VERSION`, or stamp `-ldflags "-X github.com/asalimonov/montygo.buildVersion=0.3.0"` |
| `docker pull` of the tag says `not found` while logged out | the GHCR package is still private | step 5 |
