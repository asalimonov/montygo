# Brainstorm: v0.3.0 API simplification

Date: 2026-09-15. Status: resolved; target in `20260915-v0.3.0-api-simplification-target.md`.

## 1. Initial input

Task: consider and implement a new update of the APIs based on
`../montygo-test/docs/reports/20260915-montygo-v0.2.0-api-assessment.md`,
sections "Concerns" (4) and "Recommendations for 0.3.0" (6).

User comments:

- `Run.Stop(...)` looks strange; review the naming or the shape. The concept is
  right: an application MUST NOT need verbose code for a simple operation. The
  default logic that helps belongs inside the library, not in the app.
- A declared stability boundary is postponed. APIs evolve now towards readable,
  clear, non-verbose defaults for the simple scenarios.
- A copyable example service in `examples/` is accepted: a short example that
  uses the library's default behaviour.
- v0.2.0 is clear and maintainable but too verbose. v0.3.0 focuses on handling
  default logic inside the library, keeping the API readable and understandable
  for a quick start and for maintenance in applications.

Report recommendations (6.1–6.5):

1. A high-level stop helper for the common case (`Run.Stop(ctx, StopOptions{Grace, ForceOnDeadline}) (StopSummary, error)`).
2. `InterruptOutcome.String()` and grouping predicates such as `Outcome.SessionKept()`.
3. Parameter names for methods (through `ClassInstanceOptions`) and a stub renderer that follows the documented `/` rule.
4. A declared stability boundary and a `v0.2.0` tag (boundary postponed; tag still needed).
5. A copyable example service in `examples/`.

Report concerns (4.1–4.5), condensed:

- 4.1 Consumer stop code is ~40 lines and every application repeats it: interrupt, zero-grace force at the caller deadline, wait for `RunDone`, decide who reports the run error.
- 4.2 Eight `InterruptOutcome` constants; two entry points; `InterruptPending` beside `ctx.Err()`; `Session.Err()==nil` does not guarantee admission; feed-context cancellation means three different things depending on the phase.
- 4.3 No `InterruptOutcome.String()`; stubs render `def last(self, /)`; method stubs use `arg0`; no `v0.2.0` tag.
- 4.4 The lifecycle is intricate (750 lines in `lifecycle.go` + `interrupt.go`) and has no upstream counterpart.
- 4.5 Two breaking releases in one day; acceptable before 1.0.

## 2. Current state (read-only survey)

Revision `8b86307` (v0.2.0). Relevant surface:

```go
func (s *Session) Go(ctx, code, opts *FeedOptions) *Run
func (r *Run) Done() <-chan struct{}
func (r *Run) Wait() (any, error)
func (r *Run) WaitContext(ctx) (any, error)
func (r *Run) Interrupt(ctx, InterruptOptions) (InterruptResult, error)
func (s *Session) Interrupt(ctx, InterruptOptions) (InterruptResult, error)
```

Consumer `montygo-test/runner.go` (214 lines). The stop protocol it had to write:

```go
res, err := ar.run.Interrupt(ctx, montygo.InterruptOptions{})
if err != nil {                       // InterruptPending + ctx.Err()
    res, err = r.force(ar, err)       // second Interrupt with Grace=0 and a private 1 s budget

}
```

What the library already guarantees and MUST keep (report §3): a run is
registered before `Go` returns; one interrupt request owns reason and
deadline; caller timeout does not cancel an accepted stop; old handles cannot
touch a newer execution; `SessionKilledError`, `ErrSessionBusy`; positional
stubs.

## 3. Thoughts

### 3.1 Where the verbosity comes from

The v0.2.0 API is a *mechanism* API: every fact is exposed and the caller
composes the policy. The report's ~40 lines are the policy:

| Step | Why the app writes it | Library default that removes it |
|---|---|---|
| second `Interrupt` with `Grace=0` when ctx ends | `InterruptPending` returns control while the watchdog keeps the first deadline | the stop call itself forces at its deadline |
| wait for `RunDone` | the result can arrive before the Go callback returns | the stop call waits for the run to end before returning |
| `unreportedErr` | `InterruptFinished` means "the run ended on its own; its error is in `Wait`" | the stop result carries the run error |
| `outcomeText` | no `String()` | `String()` |
| `Forced` | derived from `Outcome` | predicate on the outcome |

So the fix is not one more helper beside `Interrupt`; it is making the
*default* call complete: request, wait for cooperation, force at the deadline,
wait for the goroutine, return one small result. The mechanism stays reachable
for the rare case.

### 3.2 Why `Run.Stop(ctx, StopOptions{...}) (StopSummary, error)` reads strangely

- A second verb next to `Interrupt` doubles the vocabulary the report already
  calls too large.
- `StopOptions{ForceOnDeadline: true}` puts the safe behaviour behind a flag;
  the default (false) would be the unsafe one again.
- `StopSummary` beside `InterruptResult` is a third result type for one action.

Go idiom for "end it, with a deadline": `http.Server.Shutdown(ctx)`,
`grpc.Server.GracefulStop()`, `ticker.Stop()`. A context is the deadline;
options are rare and variadic.

### 3.3 Candidate shapes for the simple stop

A. **One verb, complete default** (recommended):

```go
// Stop ends the run: KeyboardInterrupt at the next host call or suspension,
// the worker is killed when the checkout grace expires, and Stop returns after
// the run has ended. ctx bounds only the wait; an accepted stop always completes.
func (r *Run) Stop(ctx context.Context, opts ...StopOption) (Stopped, error)

type Stopped struct {
    How  StopKind   // Aborted (session kept), Killed (session lost), Finished (ended on its own)
    Err  error      // the run's error, as Run.Wait returns it
}
func (k StopKind) String() string
func (k StopKind) SessionKept() bool

montygo.WithGrace(d), montygo.WithReason(err)   // StopOption
```

`Interrupt` (mechanism, 8 outcomes) either stays as the advanced entry point
or is folded into `Stop` options. `Session.Stop(ctx)` stops whatever runs.

B. **Keep `Interrupt` as the only verb but make it complete**: same semantics
as A under the name `Interrupt`; `InterruptOptions` becomes variadic; the
current low-level behaviour moves behind `montygo.NoWait()`. Fewer names, but
"interrupt" in Python vocabulary means the signal, not "wait until it is dead".

C. `Run.Cancel(ctx)`: Go readers expect `Cancel` to be non-blocking and
error-free (`context.CancelFunc`). It would mislead.

D. Policy on the session instead of the run: `Session.Stop(ctx)`; `Run` keeps
only `Wait`/`Done`. Simpler surface, but a stale handle could stop a newer run
again, which v0.2.0 deliberately fixed.

### 3.4 Other simplifications on the table

- Feed-context cancellation: three phase-dependent behaviours today. Candidate:
  cancelling the `Go`/`FeedRun` context behaves like `Stop` with the checkout
  grace (cooperative first, kill at grace). One rule instead of three.
- `Session.Err()==nil` does not guarantee admission: candidate `Session.Idle() bool`
  or make `Go` on a busy session return a `*Run` whose `Wait` reports
  `ErrSessionBusy` (already the case) and document it as the only check.
- One-shot convenience: `Pool.Run(ctx, code, opts) (any, error)` (checkout, feed,
  close) for scripts that need no session reuse.
- Session re-acquisition: the consumer's `ensureSession` (re-checkout when the
  session is lost) is another repeated pattern; candidate helper or leave to apps.
- `Outcome.String()`, `SessionKept()`, method parameter names, `/` rule, tags,
  `examples/service`.

## 4. Questions and answers

### Q1. Shape of the simple stop

Options: A `Run.Stop(ctx)` complete default beside the `Interrupt` mechanism;
B make `Interrupt` itself complete; C `Session.Stop` only; D `Run.Cancel`.
**Answer: A.** `Run.Stop(ctx, opts...) (Stopped, error)`, `Session.Stop(ctx)`
for whatever runs now.

### Q2. Caller ctx versus a library-owned timeout

First proposal (kill at ctx end) was rejected. **User:** the library MUST own
a default timeout policy, for instance 3 seconds: if the run has not exited by
then, kill it. This was postponed in an earlier brainstorm.

Found: `docs/brainstorms/20260915-second-stage-api-feedback.md` NOT CONSIDERED
& TODO, "Pool.Shutdown's existing post-deadline 5 s drain policy — postponed;
document separately from strict Run.WaitContext/Interrupt deadlines; do not
silently change it in this API correction", and in the target §8.7.6 / §12
"New Pool.Shutdown timeout policy — postponed; preserve/document existing
extra force grace". Related: "Forcibly preempting arbitrary Go callbacks —
too-complex; contexts remain cooperative".

Timeouts in v0.2.0 today:

| Where | Value | Meaning |
|---|---|---|
| `CheckoutOptions.InterruptGrace` | 100 ms | request → kill when the run has not ended |
| `abortDeadline` | 5 s | ceiling of one `AbortFeed` turn |
| `shutdownForceGrace` (internal/pool) | 5 s | `Pool.Shutdown`: after ctx ends, `CloseNow` on every session, then wait this long for worker exit |
| `Session.Close(ctx)` | none | waits for a running feed to end within ctx; does not stop it; ctx expiry returns `ctx.Err()` and leaves the session open |
| `Run.Stop` join of the Go callback | none | bounded only by the caller ctx |

The `Session.Close` row is a trap for simple apps: `defer session.Close(ctx)`
while a `Go` loop runs blocks until ctx expires and then fails. The consumer's
`Runner.Close` calls `Stop` before `Close` for that reason.

Derived proposal, one policy for every "end it" path:

```
StopTimeout (CheckoutOptions, default 3 s; replaces InterruptGrace 100 ms)
  t0            request: KeyboardInterrupt at the next host call / suspension;
                callback contexts cancelled
  t0+Timeout    run still not ended → kill the worker (SessionKilledError)
  after kill    wait for the Go callback goroutine to return, at most StopTimeout
                more; if it is still running, Stop returns Killed with an error
                that names the detached callback
```

- `Run.Stop(ctx)` / `Session.Stop(ctx)`: the policy above; ctx bounds only the
  caller's wait, the accepted stop always completes on its own.
- `Session.Close(ctx)`: when a feed is running, Stop first (same policy), then
  release the worker. `defer session.Close(ctx)` becomes safe.
- `Pool.Shutdown(ctx)`: close admission; Stop+Close every open session with the
  same policy; wait for worker exit. The separate 5 s `shutdownForceGrace`
  disappears; ctx bounds only the wait.
- Feed-context cancellation (`Go`/`FeedRun` ctx ends): same policy instead of
  the three phase-dependent behaviours (kill at once while Python runs today).

### Q3. One policy for Stop, Close, Shutdown and feed-context cancellation?

**User:** make it configurable for each case: global values (the default when
nothing was changed) and an override through a parameter of
`Stop`/`Shutdown`/whatever method.

Derived layering (most specific wins, zero fields inherit):

```go
// StopPolicy says how an execution is ended.
type StopPolicy struct {
    // Timeout: from the request until the worker is killed when the run has not ended.
    Timeout time.Duration
    // Join: after the kill, how long to wait for a detached Go callback to return.
    Join time.Duration
    // Reason raised in the sandbox; nil means KeyboardInterrupt.
    Reason error
}

var DefaultStopPolicy = StopPolicy{Timeout: 3 * time.Second, Join: 3 * time.Second}   // 1. global
Options.Stop / WebSocketOptions.Stop   StopPolicy                                      // 2. pool
CheckoutOptions.Stop                   StopPolicy                                      // 3. session (replaces InterruptGrace)
run.Stop(ctx, policy ...StopPolicy)                                                    // 4. call
session.Stop(ctx, policy ...StopPolicy)
session.Close(ctx, policy ...StopPolicy)      // stops a running feed first
pool.Shutdown(ctx, policy ...StopPolicy)      // per session; no separate 5 s constant
// feed-context cancellation uses the session policy (level 3)
```

`Timeout: 0` in a call means "inherit"; an explicit immediate kill is
`montygo.KillNow` (`StopPolicy{Timeout: -1}`? — to decide, see Q4).

### Q4. Four-level policy configuration

**Answer: yes** — `DefaultStopPolicy` (package var) → `Options.Stop` /
`WebSocketOptions.Stop` → `CheckoutOptions.Stop` → variadic `StopPolicy` on
`Stop`, `Close`, `Shutdown`. Zero fields inherit. `montygo.KillNow` is the
immediate-kill policy value.

### Q5. Fate of the v0.2.0 mechanism API

**Answer:** remove it. 0.x.y has no API compatibility; this is the design
stage. `Run.Interrupt`, `Session.Interrupt`, `InterruptOptions`,
`InterruptResult`, `InterruptOutcome` and its 8 constants leave the public
surface; the mechanism stays internal behind `Stop`.

Public vocabulary after Q1–Q5: `Stop`, `StopPolicy`, `DefaultStopPolicy`,
`KillNow`, `Stopped{How, Err}`, `StopKind{StopAborted, StopKilled,
StopFinished}` with `String()` and `SessionKept()`.

### Q6. Conveniences beyond stopping

**Answer:** `Pool.Run` one-shot (checkout, feed once, close with the stop
policy; `RunOptions` = checkout + feed options) and a session state predicate
(`Session.State()`: Idle | Running | Paused | Closed; `Err()` keeps the
terminal cause). The auto-reacquire wrapper is not taken.

### Q7. Parameter names for methods

**Answer:** `ClassInstanceOptions.ParameterNames map[string][]string` keyed by
sandbox method name, validated at registration like
`HostFuncOptions.ParameterNames`; the same field on `ClassTypeOptions`. The
stub renderer emits `/` only after at least one fixed parameter (`self` does
not count), fixing `def last(self, /)`.

### Q8. Example scope

**Answer:** two examples: `examples/service` (Go, Stop, Close, Shutdown, ~100
lines) and `examples/oneshot` (`pool.Run`, ~30 lines).

## 5. Verification pass

Re-reading the report, the README lifecycle section and `docs/architecture/session.md`
against Q1–Q8 gives these consequences and open forks.

Consequences (derived, no decision needed):

1. `Stopped.Err` is always what `Run.Wait` returns; `How` classifies it:
   `StopAborted` → `*RuntimeError` KeyboardInterrupt (or the reason), session
   kept; `StopKilled` → `*SessionKilledError`, session lost; `StopFinished` →
   the run's own result error (nil on success). `Session.Stop` on an idle
   session reports `StopNotRunning`. Four kinds.
2. `Stop` returns a non-nil error only for: invalid policy, `ctx.Err()` when the
   caller stopped waiting (the stop continues), `ErrCallbackDetached` when the
   worker was killed but the Go callback did not return within `Join`.
3. `abortDeadline` (5 s ceiling of one AbortFeed turn) is replaced by the
   policy `Timeout`; the AbortFeed turn cannot outlive the kill deadline.
4. `Session.CloseNow()` is replaced by `Session.Close(ctx, montygo.KillNow)`.
5. Repeated or concurrent `Stop` calls join the first request; a later call can
   only shorten the deadline (v0.2.0 rule kept).
6. The effective policy of a session is resolved at checkout
   (`DefaultStopPolicy` → pool → checkout); `DefaultStopPolicy` MUST be set
   before pools are created. Per-call values override on top.
7. `Session.State()` values: `SessionIdle`, `SessionRunning`, `SessionPaused`,
   `SessionClosed` (any terminal state; `Err()` says why).
8. `Pool.Run` applies `RunOptions.Stop` when its ctx ends and always closes the
   session before returning.

Open forks:

- F1 Feed-context cancellation (`Go`/`FeedRun` ctx ends): today three phase
  behaviours, including an immediate kill while Python executes. Proposed:
  the session policy (cooperative first, kill at `Timeout`). Consequence:
  `FeedRun(ctx)` may return up to `Timeout`+`Join` after ctx ends.
- F2 `Pool.Shutdown`: v0.2.0 waits for sessions to end on their own until ctx,
  then `CloseNow` + 5 s. Proposed: stop every running execution at once with
  the policy, close the sessions, wait for worker exit until ctx.

Answers: F1 → session stop policy (one rule); F2 → stop at once with the
policy; `CloseNow` removed in favour of `Close(ctx, montygo.KillNow)`.

## 6. NOT CONSIDERED & TODO

| # | Item | Tag | Proposed handling |
|---|---|---|---|
| N1 | Per-run policy override at `Go`/`FeedRun` time (`FeedOptions.Stop`) | potential-improvement | Not added; the session policy applies to feed-context cancellation. `Run.Stop(ctx, policy)` covers explicit stops. |
| N2 | Draining `Shutdown` (wait for natural completion until ctx, then stop) | postponed | Applications close their own sessions first, then call `Shutdown`. |
| N3 | Catchable/cooperative Python stop (`except KeyboardInterrupt`) | postponed (carried over) | AbortFeed is not catchable; a host function remains the cooperative mechanism. |
| N4 | Forcibly preempting arbitrary Go callbacks | too-complex (carried over) | `Join` bounds the wait; `ErrCallbackDetached` names the leak. |
| N5 | Auto-reacquire session wrapper (`Pool.Keep`) | potential-improvement | Not taken in Q6; `State()` + `Checkout` stay explicit. |
| N6 | Changing `DefaultStopPolicy` after pools exist | default behaviour | Resolved at checkout; documented. |
| N7 | Telemetry attribute for stop kinds (`outcome=aborted|killed`) | potential-improvement | Existing run outcome attributes stay; no new metric. |
| N8 | Migration of the `montygo-test` consumer | postponed | Outside this repository; the report's runner is the acceptance case for the README example. |
| N9 | Server-side turn/session timeouts versus the client policy | default behaviour | Unchanged; a server close arrives as `DisconnectError` (session lost) whatever the policy. |

**User:** pull N2, N3 and N5 into scope. Decisions:

- N2 → `StopPolicy.Drain`: wait `Drain` for a natural end before the request;
  default 0 at every level; used by `Stop`, `Close` and `Shutdown` alike.
- N5 → `Pool.Slot(opts) *Slot` with `Go`, `FeedRun`, `Stop`, `Close`,
  `Session`: owns at most one session, checks out lazily and again after loss
  (`State()==SessionClosed`); overlap returns `ErrSessionBusy`; sandbox state
  is not restored after a loss.
- N3 → `StopPolicy.Catchable` (default false): deliver the reason as a
  catchable Python exception at the next host call or await (resume with an
  error) instead of `AbortFeed`; the kill at `Timeout` stays. A caught
  exception followed by a normal end reports `StopFinished`; uncaught reports
  `StopAborted`.


(filled in during verification)

**N9 explained (user asked):** `monty-server` enforces its own deadlines
(`--turn-timeout`, `--session-timeout`, `--idle-timeout`, `--max-duration`).
They fire on the server and close the WebSocket with a code and reason; the
client sees `DisconnectError{Code, Reason}` and the session is lost whatever
the client's `StopPolicy` says. The policy cannot extend, shorten or
negotiate them and there is no graceful form of a server-side timeout. Not
redesigned here: clamping the client `Timeout` to the server's turn timeout
from `/info`, or a distinct stop kind for a server-side end. Consequence kept
in the target: a run the server ends while a `Stop` is in flight reports
`StopFinished` with a `DisconnectError`; therefore `Stopped` carries
`SessionErr` and `SessionKept()` is a method of `Stopped`, not of `StopKind`.

## 7. Summary

Findings:

- v0.2.0 is a mechanism API; the ~40 lines every application repeats are the
  stop *policy* (force at the deadline, join the goroutine, report the run
  error, map outcomes to text). The library owns none of it.
- Four unrelated timeouts exist (100 ms grace, 5 s abort ceiling, 5 s shutdown
  force grace, unbounded `Close` wait) and `Close` does not stop a running feed.
- Stubs render `/` after a bare `self`; methods have no parameter names.

Resolutions:

| # | Decision |
|---|---|
| 1 | `Run.Stop(ctx, policy ...StopPolicy) (Stopped, error)`; `Session.Stop` for the current execution or paused snapshot |
| 2 | `StopPolicy{Drain, Timeout, Join, Reason, Catchable}`; defaults `0 / 3 s / 3 s / KeyboardInterrupt / false`; `KillNow` |
| 3 | Levels: `DefaultStopPolicy` → `Options.Stop` / `WebSocketOptions.Stop` → `CheckoutOptions.Stop` → call; zero fields inherit; resolved at checkout |
| 4 | Removed: `Run.Interrupt`, `Session.Interrupt`, `InterruptOptions`, `InterruptResult`, `InterruptOutcome`+8 constants, `CheckoutOptions.InterruptGrace`, `Session.CloseNow`, `DurationPtr` if unused |
| 5 | `Stopped{How StopKind, Err, SessionErr}`, `Stopped.SessionKept()`; `StopKind{StopPending(0), StopNotRunning, StopAborted, StopKilled, StopFinished}` with `String()` |
| 6 | Feed-context cancellation == `Stop` with the session policy (one rule) |
| 7 | `Session.Close(ctx, policy...)` stops a running feed first; `Pool.Shutdown(ctx, policy...)` stops every session at once (optional `Drain`), no separate 5 s grace |
| 8 | `Pool.Run(ctx, code, *RunOptions)`, `Session.State()`, `Pool.Slot(opts) *Slot` |
| 9 | `ClassInstanceOptions.ParameterNames`, `ClassTypeOptions.ParameterNames`; `/` only after a fixed parameter |
| 10 | `examples/service`, `examples/oneshot`; local tags `v0.2.0` at `8b86307` and `v0.3.0` at the release commit |
